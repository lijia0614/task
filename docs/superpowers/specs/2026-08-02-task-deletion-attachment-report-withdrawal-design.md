# 任务删除、附件所有权与汇报撤回设计

## 背景与目标

本设计补充三项业务契约：

1. 任务只能由创建者本人删除，管理员没有删除他人任务的例外权限。
2. 附件只能由上传者本人删除；删除任务时必须同步删除该任务关联的 MinIO 对象和数据库记录。
3. 待审核汇报可由提交人撤回，在同一条汇报记录上编辑并重新提交，保留完整操作历史。

现有“任务存在待审核汇报时不能删除”的规则继续保留。所有变更必须通过增量迁移完成，不清空或重置现有数据库。

## 方案选择

采用显式附件关联和汇报状态机方案：

- `task_attachment` 增加 `minio_file_id`，任务附件通过主键关联上传记录，不通过 URL 猜测对象。
- `report` 增加 `WITHDRAWN` 状态，并新增 `report_history` 保存状态变化与内容快照。
- 汇报状态变化使用数据库条件更新或行锁，确保审核和撤回并发时只有一个操作成功。

不采用以下方案：

- 不从 `file_url` 长期推断 MinIO 对象名。URL 是展示字段，不应承担关系完整性。
- 不在撤回时删除原汇报并新建记录。这样会丢失汇报身份、评论关联和审计历史。

## 任务删除权限

### 权限规则

- `DELETE /api/tasks/{id}` 仅在 `task.creator_id == currentUser.id` 时允许。
- 管理员、组长和任务成员均不能删除他人创建的任务。
- 修改任务和调整权重的既有权限不在本次需求中改变；实现时将删除权限从通用 `canManage` 判断中拆出，避免误改其他行为。
- 任务不存在或已逻辑删除时返回“任务不存在”。
- 任务存在 `PENDING` 汇报时继续拒绝删除。

### 删除范围

删除任务时：

1. 校验当前用户是任务创建者。
2. 校验没有待审核汇报。
3. 读取该任务的全部 `task_attachment` 及其 `minio_file` 记录。
4. 校验每个附件均由任务创建者上传；历史脏数据若关联了他人附件，拒绝删除任务并报告异常数据。
5. 删除对应 MinIO 对象。
6. 删除 `task_attachment` 和 `minio_file` 记录。
7. 对任务执行既有逻辑删除。

任务成员、已审核汇报、评论等业务记录继续保留用于审计，但普通业务查询不能再通过已删除任务访问它们。现有逻辑删除行为不改为物理级联删除。

### MinIO 与数据库一致性

MySQL 与 MinIO 无法组成同一个原子事务，采用可重试删除策略：

- 先完成所有 MinIO 对象删除，再提交数据库删除。
- MinIO 返回“对象不存在”视为删除成功，使重试幂等。
- 任一其他 MinIO 删除失败时，不删除数据库记录和任务，接口返回失败。
- 若 MinIO 已删除但数据库事务失败，重试时把对象不存在视为成功，再完成数据库事务。

## 附件所有权与生命周期

### 数据关系

`task_attachment` 新增：

```sql
minio_file_id BIGINT NULL
```

并增加唯一索引，确保一个上传文件最多绑定到一个任务。保留现有文件名、URL、大小和上传者快照字段。

迁移流程：

1. 增加可空字段。
2. 用 `task_attachment.file_url` 末尾与 `minio_file.object_name` 精确匹配，回填历史关联。
3. 增加唯一索引。
4. 对无法回填的历史附件记录输出迁移审计结果；删除包含此类附件的任务时必须明确失败，不能猜测或静默跳过文件删除。

### 上传和绑定

- 文件上传后先作为“未绑定上传”存在于 `minio_file`。
- 创建任务时，每个 `attachmentId` 必须存在、属于当前任务创建者、且尚未绑定其他任务。
- 任一附件不满足条件时，整个创建任务请求失败，不再静默跳过无效 ID。
- `task_attachment.uploaded_by` 使用真实 `minio_file.uploader_id`。
- 绑定时在事务内锁定对应 `minio_file` 行并再次检查所有权与绑定状态；多个任务并发绑定同一文件时最多一个成功。

### 直接删除附件

`DELETE /api/files/{id}` 的契约：

- 仅 `minio_file.uploader_id == currentUser.id` 时允许，管理员没有删除他人附件的例外权限。
- 已绑定任务的附件拒绝通过该接口删除，防止破坏任务详情；绑定附件由任务删除流程统一清理。
- 未绑定附件先删除 MinIO 对象，再删除 `minio_file` 记录。
- 对象不存在视为成功，其他 MinIO 错误保留数据库记录并返回失败。
- 删除时锁定 `minio_file` 行，并在锁内检查是否已绑定任务，避免与创建任务并发时一边绑定、一边删除。

### 创建页临时附件

- 同一 `file.uid` 只允许触发一次上传。
- 上传中移除时优先取消请求；如果服务器已经完成并返回文件 ID，立即调用本人附件删除接口清理。
- 已上传但尚未创建任务的附件被移除或用户取消创建时，调用本人附件删除接口。
- 清理失败时明确提示，并保留可重试的附件项；不能静默隐藏并留下无主文件。
- 创建任务成功后不再由页面清理这些附件，因为它们已绑定到任务。

## 汇报撤回状态机

### 状态转换

允许的转换：

```text
PENDING -> APPROVED
PENDING -> REJECTED
PENDING -> WITHDRAWN
WITHDRAWN -> WITHDRAWN  (编辑内容或进度，不改变状态)
WITHDRAWN -> PENDING    (重新提交)
```

其他转换全部拒绝。已通过或已驳回的汇报不能撤回或重新编辑。

### 权限与可见性

- 只有汇报提交人可以撤回、编辑和重新提交自己的汇报。
- 只有 `PENDING` 汇报可以撤回。
- 只有 `WITHDRAWN` 汇报可以编辑或重新提交。
- `WITHDRAWN` 仅提交人可见，从待审核列表立即消失。
- `PENDING`、`APPROVED`、`REJECTED` 的既有可见性规则保持不变。
- 与撤回汇报关联的评论不删除，但撤回期间不向其他用户暴露。

### 进度规则

- 编辑和重新提交的目标进度必须不低于当前 `task_member.progress`，且不超过 100。
- 撤回不修改成员进度、任务总进度或任务完成状态。
- 重新提交清空旧的审核结果字段：`reviewer_id`、`review_comment`、`reviewed_at`、`final_progress`。
- 同一任务成员同一时间最多存在一条 `PENDING` 汇报。

为避免并发重复待审，提交新汇报和重新提交都必须锁定对应 `task_member` 行，在同一事务中检查是否已有 `PENDING` 记录后再写入。

### 并发规则

撤回、通过和驳回可能同时发生。三个操作均须在 SQL 更新条件中包含 `status = PENDING`，或先锁定同一汇报行：

- 最先完成状态转换的操作成功。
- 后续操作因状态已变化而失败，返回明确的“汇报状态已变化，请刷新”。
- 不允许审核成功后又被撤回，或撤回后仍被审核。

## 汇报历史

新增 `report_history`：

```sql
CREATE TABLE report_history (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  report_id BIGINT NOT NULL,
  action VARCHAR(20) NOT NULL,
  content TEXT NOT NULL,
  progress INT NOT NULL,
  actor_id BIGINT NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_report_history_report (report_id)
);
```

`action` 取值：`SUBMITTED`、`WITHDRAWN`、`EDITED`、`RESUBMITTED`、`APPROVED`、`REJECTED`。每次成功操作后，在同一数据库事务中记录操作完成后的内容和进度快照；`APPROVED` 的进度记录审核后实际采用的 `finalProgress`，其余动作记录汇报请求进度。历史仅作为审计数据，本次不增加独立的普通用户历史页面。

## API 契约

保留现有接口，并新增：

```text
POST /api/reports/{id}/withdraw
PUT  /api/reports/{id}            body: { content, progress }
POST /api/reports/{id}/resubmit
```

- `withdraw` 只执行 `PENDING -> WITHDRAWN`。
- `PUT` 只在 `WITHDRAWN` 状态修改内容和进度。
- `resubmit` 验证当前内容和进度后执行 `WITHDRAWN -> PENDING`。
- 所有接口先校验资源所有权，再返回状态错误，避免向未授权用户泄露汇报状态。

前端任务详情页在本人汇报上提供：

- `PENDING`：显示“撤回”命令。
- `WITHDRAWN`：显示“编辑并重新提交”命令。
- 撤回和重提期间禁用重复操作，并在成功后刷新汇报列表。

## 测试与验收

### 后端自动化测试

- 创建者可删除自己的任务；管理员和其他用户删除他人任务返回 403。
- 有待审核汇报时创建者也不能删除任务。
- 创建任务不能绑定他人上传、缺失或已绑定的附件。
- 上传者可删除自己的未绑定附件；他人和管理员均不能删除。
- 已绑定附件不能直接删除。
- 删除文件和删除任务会调用正确 bucket/objectName 的 MinIO 删除。
- MinIO 普通失败时数据库和任务状态不变；对象不存在时删除幂等成功。
- 待审核汇报可由本人撤回，其他人不可撤回；审核后不可撤回。
- 撤回后可编辑和重新提交，审核字段被清空，历史记录完整。
- 撤回状态不出现在待审核列表且仅本人可见。
- 撤回与审核并发时只能有一个状态转换成功。
- 同一任务成员不能同时存在多条待审核汇报。

MinIO 使用 mock 验证调用，不连接或删除真实开发环境对象。数据库测试必须记录并清理自身数据，不清理现有开发数据。

### 前端验收

- 创建页通过请求拦截/mock 验证上传、移除、取消和创建，不真实写数据库或 MinIO。
- 390px 和桌面视口无横向溢出，上传和提交 loading 状态稳定。
- 后续任务详情页验证撤回、编辑和重新提交的按钮可见性及错误恢复。
- 生产构建和 `git diff --check` 通过。
